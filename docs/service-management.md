# Service management

AutoCAD uses the shared framework 0.20 management/resource interface. It reports to the independent Windows MCP Service Manager; AutoCAD setup does not install or launch another manager. The standalone plugin and native tool schemas remain independent. See [resource ownership](resource-ownership.md) for exact launch coverage and acceptance limits.

## Owning processes

Each direct `serve` process registers for its lifetime with a random instance ID and canonical plugin ID `autocad@autocad-local`. Multiple direct processes have separate rows; status does not assert ownership of another process's work. The experimental host/proxy CLI is blocked pending its SDK stdio ownership adapter. Its source management adapter remains available for isolated assessment, without a deployment acceptance claim.

The default private registry uses the Windows Local AppData known folder without package redirection, followed by `CodexMCPManager/Registry`. The framework supplies authenticated literal-loopback endpoints, private registry ACLs, bounded JSON and a durable restart journal. Tokens and runtime files remain outside public source and logs. `--management-registry ABSOLUTE_PRIVATE_DIRECTORY` on an owning serve command, or `AUTOCAD_MCP_MANAGEMENT_REGISTRY`, selects a separate registry for isolated testing. Neither changes an MCP endpoint or configures an external broker.

The management callback reads only cached component metadata and synchronized in-memory request counters. Pending and active requests, including control requests and owned index jobs, count as work. A separate bounded background refresh reads installed distribution metadata, local publisher version metadata and the fixed read-only Codex plugin inventory. It does not read drawing content, attach AutoCAD, contact controllers or poll package feeds. Inventory failures mark cached data stale. Unknown availability remains unknown; update-pending flags use explicit numeric local-version comparisons. Installed and running versions remain distinct.

Generated plugin bindings identify their canonical package version through `AUTOCAD_MCP_PLUGIN_VERSION` and padded display stamp through `AUTOCAD_MCP_PLUGIN_DISPLAY_VERSION`. The manager message includes the running app display stamp; component versions use canonical numeric identities and semantic comparisons. See [release versions](versioning.md). A manually started process leaves that value unknown. Framework and SDK availability remain unknown without a configured release source. Updating native plugin bytes still needs installation and host reload.

## Restart boundary

Restart remains disabled. AutoCAD has no surviving supervisor and no atomic cross-chat quiescence fence covering other processes' leases, queued work, prepared actions and unresolved native effects. Status includes this specific reason. No management request saves or closes AutoCAD, kills a process, guesses a launch command, retries an operation or clears a receipt.

The framework commits restart intent before admission and preserves duplicate-ID receipts and app-wide uncertain barriers across process lifetimes. AutoCAD supplies only a blocked `RestartResult`; no native restart effect is enabled. App-only `pending_restarts()` and `reconcile_restart()` are inherited framework APIs for a future independently verified operator workflow, not exposed MCP or tray actions. Restart acceptance and replacement health are separate facts; no real restart acceptance is claimed here.

## Process lifetimes and shutdown

The 0.6 source introduces fail-fast server leases before loading the drawing service. `max_server_instances` defaults to two and accepts 1..8. Direct services and app hosts share the owner pool for the configured state; app-host backends have a separately bounded pool. A host also holds an exclusive lease for its host-state path. Fixed proxies have a two-instance pool per host state. OS-held locks release on process exit; a full pool rejects startup instead of queuing another server or starting a replacement. Request, worker and ODA limits remain separately enforced. These are per-state bounds; unrelated installations and arbitrary new state directories are outside this fence.

CLI servers capture their immediate parent at startup. On Windows the monitor retains a process handle and checks its creation time, avoiding later PID/name-based cleanup. Stdio pipe checks do not consume protocol bytes. Parent loss or a closed protocol writer gives normal shutdown three seconds, then terminates only this server with exit code 70. A Windows virtual-environment launcher can remain alive after its own caller exits; the default plugin's independent stdio EOF fence covers that case. An HTTP owner has no stdio fence and still requires an explicit operator-owned service/terminal lifecycle; parent monitoring alone does not establish a surviving supervisor. Running native work can remain uncertain; inspect its original receipt and native state before any further action.

Extraction, rendering, table detection, highlighting helpers and ODA conversion use one owned-process runner. On Windows 10+ a noninherited Job Object is assigned through the process-creation job-list attribute before child code runs. Its last-handle close terminates app-created descendants, including on abrupt owner death; assignment failure rejects launch. Each job caps active processes at eight. Only private capture pipes and disconnected stdin are inherited. Diagnostic tails are bounded in memory, normally to 64 KiB per stream; Codex inventory has a fixed 2 MiB budget and rejects truncation. Existing native AutoCAD sessions are not assigned to these jobs. The POSIX fallback cleans process groups on return/deadline; abrupt-parent cleanup there is outside the Windows acceptance profile. See Microsoft's [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects) and [process attribute contract](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute).

An index-job owner stops admission during normal shutdown, requests cancellation only for its own jobs and bounds thread joins. Queued jobs cannot start extraction; running files may already have committed. Hard termination releases kernel-owned descendants and leaves durable in-flight intent available for uncertainty inspection. Nothing clears journals, automatically retries writes, selects another route, launches a manager or starts a replacement server.

Shared `ResourceLedger`/`ResourceOwner` records retain exact host/PID/creation/image identities and supervisor generations. Workers start suspended; durable binding precedes resume, and failure closes containment without fallback. Nested helpers remain in the original supervisor's recorded named job. `cad_status` and management read bounded cached summaries. The server durably registers native AutoCAD as a protected attachment before display dispatch, then releases its COM/ledger claim without Quit/Close/save. Unknown outcomes retain native barriers and operation receipts. No shared native launch or ownership transfer is supported.

The registry is durable private JSON, independent of the live endpoint. Reviewed harmless orphan recovery is tested against shared 0.20; manager UI/installed/native acceptance remains separate. Kernel Job Objects cover abrupt Windows owner exit for app-created workers, without establishing ownership of pre-existing software. The original operation/job journals remain authoritative for engineering effects. History is retained rather than automatically archived to free admission.

Pure/stub and harmless Windows process fixtures cover source ownership and cleanup. Real MCP/Codex EOF/reconnect, deployment, manager UI and native AutoCAD acceptance remain unassessed. `cad_capabilities` distinguishes those boundaries and the blocked experimental host. See the [launch-path inventory](resource-ownership.md#launch-paths) before selecting a profile.

## Observation and checks

When the plugin starts its stdio service, its live management row reports running or busy after metadata refresh. Closing that owner leaves a stopped registration; an interrupted process becomes offline. Installing an enabled plugin does not start a service. The manager can show an installed plugin as not reporting until an owner runs. AutoCAD does not start a background drawing service solely to populate the tray.

Use synthetic input and a dedicated registry for `tests/test_management.py`, protocol and framework checks. Verify cached versions, unknown availability, source updates, active requests, stale and concurrent restart refusals, zero native effects, uncertain intent survival and clean owner shutdown. Run the upstream pinned `tests/test_management.py` separately for synthetic accepted restart counts, authentication and durable journal contracts. Real native restart, multi-chat supervisor fencing and host UI rendering remain acceptance work. See the [upstream contract](https://github.com/votecoffee/CodexMCPBroker/blob/5b2cac50ca24d21a15b732e0424bb02fd794e1fb/docs/service-management.md).
