# Concurrent requests and operation receipts

Version 0.3 runs blocking MCP operations in a bounded thread pool. HTTP sessions and stdio callers can overlap requests. Separate plugin/chat processes coordinate through the same configured app-state directory. Extraction, rendering, PDF tables and AutoCAD highlighting run in bounded child processes. Transport handling stays available while those workers run.

## Limits and resource ownership

| Resource | Default | Scope |
| --- | --- | --- |
| Active normal requests | 4 | Each MCP process |
| Waiting normal requests | 32 | Each MCP process; excess requests receive a busy error |
| Control calls | 2 active, 8 admitted | Separate per-process capacity for status and transaction lookup |
| Child workers | 4 | Shared by all processes using one state directory |
| ODA conversions | 1 | Shared by state directory; other worker slots remain available |
| AutoCAD UI operations | 1 | Serialized across processes using the state directory |
| Resource wait | 180 seconds | Configurable, distinct from a worker's execution timeout |

Configure `max_concurrent_requests`, `max_queued_requests`, `max_worker_processes`, `max_oda_processes` and `lock_timeout_seconds` in the private configuration. Keep settings consistent across all processes sharing a state directory, and restart them when changing limits. Only processes using this server and state directory participate; external AutoCAD automation is outside these locks.

`cad_concurrency_status` reports active/queued counts for the answering MCP process and shared worker limits. It does not claim to count all requests in other chats. `cad_status` reports configured concurrency settings. Control calls use separate admission capacity so extraction saturation does not put them behind the normal work queue.

Same-content cold extraction is coordinated by a content-key lock: one process publishes the cache, and other callers reuse it. Cache and snapshot publication uses atomic replacement. The index uses SQLite WAL, explicit per-file write transactions, and a consistent read transaction for search metadata and records. Failed index replacement rolls back its rows and source metadata. Connections are closed after each transaction. Existing project snapshots cannot be overwritten with different content under the same ID.

OS locks release when an owner process exits. Lock files remain in app state; their existence alone does not mean a resource is locked. There is no time-based lock stealing or unsafe deletion of a live owner's lock.

## Durable request IDs

All five state-changing tools accept an optional `request_id`: indexing, preview creation, electrical building, export and source highlighting. Use a unique ID for each intended operation and retain it before dispatch. The response includes a `transaction` receipt with the ID, operation, state, timestamps and replay flag. An omitted ID is generated by the server; supply one when a caller needs recovery after a lost response.

```json
{
  "project_id": "project_0123456789abcdef01234567",
  "request_id": "export-review-2026-01"
}
```

For `cad_export_electrical_project`, sending the same ID and identical arguments again returns the recorded artifact path and hash, with `replayed: true`. It does not create another export. A different argument set under that ID is rejected. IDs are shared by all clients of the configured state directory; prefer UUIDs or another suitably unique scheme. Explicit default values and omitted defaults are normalized before fingerprinting.

Replayed responses retain their original timestamps and as-of freshness observations. Use a current read operation when the caller needs to verify source freshness again.

Call `cad_get_transaction` after a timeout or disconnect. Set `include_result=true` for a recorded result. Lookup never dispatches the original operation.

| State | Meaning |
| --- | --- |
| `not_found` | No execution receipt exists yet; a request may still be waiting for admission. A same-ID retry remains safe. |
| `running` | The execution owner holds the request lock. |
| `succeeded` | The operation returned and its result was committed. Inspect per-file statuses and interpretation limits in that result. |
| `failed` | An error or failure result was recorded. Partial app-state work may exist; the same ID is not executed again. |
| `unknown` | An owner disappeared or an operation reported an uncertain outcome. Inspect effects before considering another request. |

An owner that disappears after publishing an artifact but before recording completion produces an unknown outcome. The server does not infer that the operation was rolled back. A client cancellation does not abandon a running worker; its result can still be recorded. Process shutdown can interrupt work, so recovery uses the durable receipt and owner-lock check. Request records survive server restarts. Results are bounded to 185 KB before receipt metadata; larger write responses fail explicitly and require state inspection.

## Transaction boundaries

Index batches commit each file independently. Snapshots and exports publish complete JSON files, with export readback verification. A whole drawing root is not one rollback transaction, and JSON publication and the receipt journal are not a distributed commit: a crash between them is deliberately reported unknown. Source drawings are preserved. AutoCAD highlighting changes display state and has no transactional rollback; native drawing-edit transactions are not exposed.

Concurrency does not resolve a source drawing being edited externally. Hash checks detect changes around extraction and publication; current-source checks flag stale snapshots and indexes. Native report assertions and geometry interpretation retain their existing evidence limits.

## Verification

The synthetic suite exercises cross-process lock release after termination, shared capacity, duplicate cold-cache coalescing, index rollback after a partial insert, duplicate request replay, argument conflicts, interrupted-owner recovery and client cancellation. A blocked-operation test verifies that MCP control calls still complete. A real two-process stdio test concurrently indexes/builds/exports through two clients sharing state and verifies one export for one request ID. These tests cover server coordination; live AutoCAD behavior requires separate native validation.
